# Dashboard API and interface

`GET /api/v1/dashboard?zone=CENTRAL` accepts only an optional normalized zone; unknown/repeated filters return 400. No actor is required for reads. Response is 200 `{data:{total,awaitingAssignment,inProgress,byStatus,attention,attentionTotal,asOf}}`. All eight byStatus keys are present, including zeros. Awaiting assignment means NEW + READY_FOR_ASSIGNMENT; in progress means ACCEPTED + PICKED_UP. Manual work is counted separately. Zone means pickup OR destination.

Counts and attention share one snapshot transaction. Attention includes manual jobs, nonterminal jobs with a reached delivery deadline, and pending confirmations with reached attempt expiry. Priority of explanations is manual reason, deadline overdue, then confirmation overdue. A due confirmation remains AWAITING_CONFIRMATION until the worker commits; the dashboard does not fake expiry. `attention` is at most 20 oldest-received rows with job DTO fields plus attentionReason; attentionTotal reports all matches. The UI highlights the first five and provides full operational queues below. The aggregation joins current attempts by indexed ID without loading scoring snapshots. Queries are bounded to five seconds; volume optimization remains a future task.

The React desk polls GETs every five seconds, aborts obsolete reads and keeps read errors visible. It never polls audited recommendations. Job/reference, status and zone filters, manual age/reasons/failed commands, rider configuration/workload, scores/exclusions/overrides, rider simulation and all delivery commands use real APIs. History and active workload are paginated. Numeric details are preserved in stored snapshots, not recomputed from current riders.

Assignment keys and exact payloads are retained before sending, including localStorage recovery after a page reload. A network failure or server 5xx offers **Retry exact assignment**; a definitive 4xx permits a corrected new action. Polling may reveal a committed assignment before recovery; its original key still recovers the receipt. Old advice is invalidated when job version changes. Buttons prevent duplicate submissions; server guards remain authoritative across tabs and dispatchers. Demo rider actions are labeled simulation and supply rider actor IDs.

## Refresh and action feedback

The main queue remains mounted during successful background revalidation and manual refresh. A filter change retains the preceding collection with an updating indicator until its replacement arrives; switching collection starts an initial skeleton. Read failures retain the last successful data and a persistent error with **Retry read**. Manual **Refresh** reports completion only after dashboard, queue and fleet reads settle. A full browser reload starts with the normal initial skeleton; no server data is persisted in browser storage.

Job/rider/create screens use a native modal side panel. The surrounding desk remains visible and inert. Escape, backdrop or Close returns to the workspace; explicit cleanup restores the opener's focus. Form inputs survive GET polling and remain on validation/conflict failures. User changes are never silently discarded by a background refresh. Closing an unsaved panel discards its local draft; no cross-reload draft persistence is promised.

Every mutation exposes its own pending label and disables duplicate submission. Lifecycle screens also show an inline pending explanation, persistent outcome/error and a global dismissible notification. Notifications survive form replacement and appear above the active modal backdrop; the visible stack is bounded to three and auto-dismisses after eight seconds without a new notice. Successful mutation DTOs update detail state immediately; a write epoch rejects older in-flight GET results, then background reads refresh aggregates. Network uncertainty is explained without claiming success, and exact assignment recovery retains its original receipt.

The interface uses responsive CSS, local SVG icons and native dialog/fetch/React state without another component library. Motion is limited to brief panels, notifications and loading indicators; `prefers-reduced-motion` disables it. Tables scroll within their own container on narrow screens rather than widening the page.
